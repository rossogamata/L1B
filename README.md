## Навчальний кластер Kubernetes на Proxmox

### Цільова схема для демонстрації

- Один control-plane вузол та два worker-вузли як окремі віртуальні машини.
- Linux-система на базі Debian або Ubuntu, `containerd` як container runtime.
- Kubernetes, встановлений через `kubeadm`, і мережевий плагін, наприклад Flannel.
- Terraform створює віртуальні машини на Proxmox; Ansible готує ОС та встановлює/налаштовує Kubernetes.
- Курсантам надається доступ до кластерного API з робочої мережі лабораторії, а не до облікового запису Proxmox.

Перед заняттями я готую шаблон VM із cloud-init, адресний план, DNS/маршрутизацію, доступ до репозиторіїв пакетів і образів, а також перевіряю квоти CPU, RAM і сховища. Для невеликої аудиторної групи доцільніше мати один спільний кластер і виділяти кожному курсанту або парі окремий namespace. Якщо кластером користуються кілька груп одночасно, слід передбачити quotas/limits та очистку ресурсів між потоками.

### Розподіл відповідальності інструментів

1. **Terraform**: створення/видалення VM, дисків, мережевих інтерфейсів і cloud-init параметрів через API Proxmox. Версії провайдера та схема ресурсів залежать від установленого Proxmox і мають бути зафіксовані в конфігурації.
2. **Ansible**: перевірка передумов ОС, налаштування swap і мережевих параметрів, встановлення `containerd` та компонентів Kubernetes, ініціалізація control plane, приєднання worker-вузлів і встановлення CNI.
3. **kubectl та YAML**: робочий інструмент курсантів після моєї перевірки готовності всіх вузлів.

### Послідовність моєї демонстрації

1. Пояснити схему мережі, адреси VM і призначення трьох вузлів. Перевірити наявність шаблону VM, SSH-доступу, DNS та потрібних ресурсів Proxmox.
2. Перед запуском Terraform показати конфігурацію та план змін; перевірити, що він стосується лише навчальних VM. Не виводити значення секретів.
3. Створити VM і перевірити їхню доступність та імена вузлів. Показати, що Terraform керує інфраструктурою, але сам по собі не встановлює Kubernetes.
4. Показати inventory/групи Ansible та етапи налаштування вузлів: runtime, мережа й передумови `kubeadm`, control plane, worker join і CNI.
5. Після завершення автоматизації перевірити вузли та системні компоненти командами з розділу готовності кластера. Видавати курсантам доступ лише після успішної перевірки.
6. Наприкінці циклу видаляти навчальні VM контрольованим запуском Terraform, попередньо перевіривши план знищення та відсутність потрібних даних на цих ресурсах.

Не зберігайте Proxmox API tokens, SSH private keys, kubeconfig із адміністративними правами чи паролі в Git. Використовуйте секрети середовища/CI або сховище секретів. API Proxmox і Kubernetes не слід відкривати до публічного інтернету. У лабораторії варто використовувати окрему VLAN/мережу, обмежені права, квоти та план відновлення VM.

Повний навчальний приклад Terraform та Ansible для створення цього кластера: [код заняття 3](lesson-03-cluster/README.md).

### Перевірка готовності кластера

Перед практикою я перевіряю:

```bash
kubectl get nodes -o wide
kubectl get pods -A
kubectl get storageclass
```

Усі вузли мають бути `Ready`, системні Pod-и — без помилок, а DNS усередині кластера — працювати. Для вправ із томами потрібен доступний StorageClass; якщо його немає, вправи з persistent storage слід залишити демонстраційними й не блокувати основну практику.

## Оцінювання

Програма містить 4 практичні заняття по 20 балів (80) і 6 групових занять по 4 бали (24). Разом виходить 104 сирих бали. Оскільки окремого правила перерахунку в програмі немає, у цих матеріалах використано прозоре припущення: **підсумкові бали = сирі бали × 100 / 104**, із округленням до цілого за звичайним математичним правилом. Допуск до заліку — підсумкові 50 зі 100, тобто не менше 52 сирих балів до перерахунку. Якщо кафедра затвердить іншу шкалу, достатньо замінити цей коефіцієнт і поріг у відомості.

| Складова | Кількість | За одне | Сирий максимум |
|---|---:|---:|---:|
| Практичні заняття | 4 | 20 | 80 |
| Групові заняття | 6 | 4 | 24 |
| **Разом** |  |  | **104** |
| Підсумкова оцінка після перерахунку |  |  | **100** |

У кожному плані практичного заняття наведено критерії на 20 балів, а в групових — на 4. Підсумкове заняття містить рекомендації до диференційованого заліку. Його формат і можливе окреме оцінювання потрібно узгодити з локальними правилами закладу; окремі бали за залік тут не додано, щоб не перевищувати заявлений максимум.

## Як проводити практичні

- Практичні можна виконувати індивідуально або в парах; оцінюється персонально підтверджений внесок кожного курсанта.
- На початку заняття я видаю namespace та kubeconfig із мінімально необхідними правами або призначаю ізольований Docker host.
- Курсант здає YAML/файли конфігурації, вивід контрольних команд і коротке пояснення. Не здавати токени, приватні ключі чи повний kubeconfig.
- Перед наступним заняттям я очищую тестові ресурси або перевіряю, що курсанти видалили їх самостійно.
